1. 总览：两个角色、两条链路

角色做什么接口鉴权
设备端（被控客户端） 与服务器建立一条长连接，上报自己能被调用的方法名；保持在线，等待服务器下发调用。 SignalR Hub
/chathub		 无 HTTP Basic 鉴权（见下方安全提示）
调用端（管理后台 / 运维脚本） 调用在线设备上报过的某个方法并同步等待返回值：带 deviceId 时把候选限定在该设备 ID 的连接内（同 ID 多条连接则随机选一条）；不带时在所有上报了该方法的在线连接中随机选一条。 POST /api/invoke HTTP Basic

一次完整的调用链路是：

调用端 ──HTTP/2 + Basic Auth──▶ 服务端 /api/invoke
                                      │
                                      │ 选目标：
                                      │   带 deviceId → 精确指定该在线设备
                                      │   不带        → 在支持该 method 的在线设备中随机选一台
                                      │
                                      │ 白名单校验（设备上线时上报的方法）
                                      ▼
                                  SignalR 长连接（/chathub）
                                      │  server → client 调用，等待返回值
                                      ▼
                                   设备端 Handler
                                      │
                                      └── 返回值 ──▶ 服务端 ──▶ HTTP 200 JSON
                                                                    （回显实际承接调用的 deviceId）

安全提示：/chathub 本身不做 HTTP Basic 鉴权，能访问到服务端端口的人都可以注册成设备。因此：

  • 不要把服务端端口直接暴露到公网；应放在防火墙 / 内网 / 反向代理之后。
  • /api/invoke 的口令只是管理面凭据，不能替代对 /chathub 的网络层访问控制。

2. 前置约定：HTTPS / HTTP/2 / 口令

2.1 协议与端口

  • 服务端 Kestrel 配置为 HTTPS + HTTP/2 only（HttpProtocols.Http2）。客户端必须使用 https://，并且实际协商到 h2。
  • 生产环境默认地址：https://<服务器地址>:6099（见服务端 appsettings.json 的 Urls）。
  • HTTP/1.1 客户端会被直接断开（实测 curl 走 HTTP/1.1 报 Recv failure: Connection was aborted）。

2.2 自签名证书

服务端启动时会在程序目录的 ssl/ 下生成或读取 https-certificate.pfx。本地联调时客户端应跳过证书校验（生产环境建议把该自签名证书导入信任链，或替换为正式证书）。

2.3 管理面口令

服务端启动时会把一枚口令写入服务端程序目录下的：

ssl/client-password.txt

该口令的值是服务端证书原始字节的 SHA-256（大写十六进制字符串），不是 pfx 的导入密码。调用 /api/invoke、/api/devices、/api/status 时：

Authorization: Basic Base64(UTF8("任意用户名:" + client-password.txt 的内容))
  • 用户名任意（服务端只取冒号之后的部分作为口令），例如 admin:<口令>。
  • 口令按文件内容原样使用，不要改写大小写。
  • 管理接口不做回环豁免：即使从服务器本机访问，也要带凭据。
  • 口令错误或缺少凭据统一返回 401，并带 WWW-Authenticate: Basic realm="admin"。

3. 设备端：连接 ChatHub

3.1 连接 URL

https://<服务器地址>:6099/chathub?info=<URL 编码后的 info JSON>

info 是明文 JSON（不是 base64、不是 protobuf），必须做 URL 编码。服务端会把它解析成设备信息并写入在线表；解析失败或缺 deviceId 会直接拒绝连接。

3.2 info 字段

字段类型必填说明
deviceId string 是 设备标识。同一个 deviceId 允许多条连接同时在线（重连、同机多实例等），服务端按 connectionId 分别记录，互不覆盖。
machineName string 否 机器名，仅用于管理页展示。
userName string 否 用户名，仅用于管理页展示。
methods string[] 否 设备主动上报的、允许服务端调用的方法名列表。 /api/invoke 只会放行这个列表里的方法。没上报的连接不会成为任何调用的候选；若某个 deviceId 下的所有连接都没上报，精确调用该 ID 会得到 409。

示例（URL 编码前）：

{
  "deviceId": "pc-001",
  "machineName": "PC-001",
  "userName": "alice",
  "methods": ["Ping", "Echo"]
}

JSON 键名大小写不敏感：deviceId 与 DeviceId 都能识别。推荐统一用 camelCase。

3.3 服务端校验与生命周期

情况结果
缺少 info 查询参数连接被拒（服务端抛 缺少info），客户端 StartAsync 失败。
info 不是合法 JSON连接被拒（info不是合法JSON）。
deviceId 缺失或为空白连接被拒（info缺少deviceId）。
同一个 deviceId 再次上线允许。新连接与已有连接同时在线，各自有独立的 connectionId；管理页会显示为多行。
连接断开（主动关闭 / 网络中断 / 服务端回收）只从在线表移除这条连接自己，同 deviceId 的其它连接不受影响。若该 ID 已无任何连接，精确调用它会返回 404。

3.4 C# 连接示例

需要 NuGet 包：

<PackageReference Include="Microsoft.AspNetCore.SignalR.Client" Version="10.0.12" />
using Microsoft.AspNetCore.Http.Connections;
using Microsoft.AspNetCore.SignalR.Client;
using System.Net;
using System.Text.Json;

const string server = "https://127.0.0.1:6099";

// 1) 构造 info（必须 URL 编码）
var info = JsonSerializer.Serialize(new
{
    deviceId = "pc-001",
    machineName = Environment.MachineName,
    userName = "alice",
    methods = new[] { "Ping", "Echo" }
});
var url = $"{server}/chathub?info={Uri.EscapeDataString(info)}";

// 2) 自签名证书校验放在 SocketsHttpHandler 上：
//    negotiate 请求和 HTTP/2 WebSocket 共用这个 handler
SocketsHttpHandler NewHandler() => new()
{
    SslOptions = { RemoteCertificateValidationCallback = (_, _, _, _) => true },
    EnableMultipleHttp2Connections = true
};

var connection = new HubConnectionBuilder()
    .WithUrl(url, options =>
    {
        options.Transports = HttpTransportType.WebSockets;

        // 提供 handler 后，SignalR 建立 WebSocket 时会用它构造 HttpMessageInvoker
        //（HTTP/2 WebSocket 必需的 invoker 由此而来）；negotiate 请求也用它
        options.HttpMessageHandlerFactory = _ => NewHandler();

        // 告诉 ClientWebSocket 必须走 HTTP/2，禁止回退到 1.1
        options.WebSocketConfiguration = ws =>
        {
            ws.HttpVersion = HttpVersion.Version20;
            ws.HttpVersionPolicy = HttpVersionPolicy.RequestVersionExact;
        };
    })
    .WithAutomaticReconnect()
    .Build();

await connection.StartAsync();
Console.WriteLine($"已连接，connectionId={connection.ConnectionId}");

实测：以上代码可以连上本机 https://127.0.0.1:6110 的服务端（Debug 构建），StartAsync 成功，ConnectionId 有值。

3.5 HTTP/2 WebSocket 的配置要点（含实测矩阵）

服务端是 HTTP/2 only，所以 SignalR 的 WebSocket 传输实际走的是 RFC 8441（WebSocket over HTTP/2）。.NET 的 ClientWebSocket 在 HttpVersion = 2.0 时必须通过带 HttpMessageInvoker 的重载建立连接：

// HTTP/1.1 路径：ClientWebSocket 自己建 HTTP 栈
ConnectAsync(Uri, CancellationToken)

// HTTP/2 路径：HTTP 栈（TLS、连接、生命周期）由调用方提供
ConnectAsync(Uri, HttpMessageInvoker, CancellationToken)

在 SignalR 10.x 中，有两种写法可以满足这个要求。实测矩阵如下（服务端为 H2-only，自签名证书）：

配置结果
HttpMessageHandlerFactory + WebSocketConfiguration（HttpVersion=2.0，证书配置在 handler 上） 成功推荐
同上，但还在 ClientWebSocketOptions 上设置 RemoteCertificateValidationCallback 失败：... must not be set on ClientWebSocketOptions when an HttpMessageInvoker instance is also specified.
只设 WebSocketConfiguration（HttpVersion=2.0），不配 HttpMessageHandlerFactory 失败：An HttpMessageInvoker instance must be passed to ConnectAsync when using HTTP/2.
只配 HttpMessageHandlerFactory，不设置 HttpVersion（默认 1.1） 失败：服务端断开连接（H2-only 不接受 HTTP/1.1）
WebSocketFactory + 自己创建 HttpMessageInvoker（见下方替代写法） 成功

推荐写法（即 3.4 的示例）

配置了 HttpMessageHandlerFactory 后，SignalR 会用该 handler 构造 WebSocket 连接所需的 HttpMessageInvoker；WebSocketConfiguration 只负责声明"必须走 HTTP/2"。证书、代理、Cookie、客户端证书这些与 HTTP 栈相关的配置都必须放在 handler 上，不能放在 ClientWebSocketOptions 上——否则会触发上面第二条冲突异常。

替代写法：WebSocketFactory

如果你需要完全控制 WebSocket 的创建过程（或使用较旧版本的 SignalR 客户端），也可以自己传 invoker：

// invoker 要活到连接结束，不能 connect 完就 Dispose
var wsInvoker = new HttpMessageInvoker(NewHandler(), disposeHandler: true);

options.WebSocketFactory = async (context, cancellationToken) =>
{
    var ws = new ClientWebSocket();
    ws.Options.HttpVersion = HttpVersion.Version20;
    ws.Options.HttpVersionPolicy = HttpVersionPolicy.RequestVersionExact;
    // 传了 invoker 后，证书校验只能配在 handler 上
    await ws.ConnectAsync(context.Uri, wsInvoker, cancellationToken);
    return ws;
};

两种写法等价，任选其一即可；不要在 WebSocketFactory 里再设置 ws.Options.RemoteCertificateValidationCallback。

关于协商（negotiate）：默认会先向 /chathub/negotiate 发一次 HTTP 请求，拿到分配好的 ConnectionId。这个请求由 SignalR 的 HttpClient 发出，同样需要能通过自签名证书校验（所以用 HttpMessageHandlerFactory 提供 handler）。

也可以设置 options.SkipNegotiation = true; 直接建立 WebSocket（仅 WebSockets 传输允许）。实测同样可以连通；区别是客户端拿不到协商分配的 ConnectionId（connection.ConnectionId 为空），需要时可通过 /api/devices 查询服务端实际分配的 ID。注意：即使跳过协商，HttpVersion=2.0 仍需要 handler 或显式 invoker，二选一。

3.6 重连

建议启用 WithAutomaticReconnect()。重连时客户端会复用同一个 URL（同一个 info），服务端会重新登记设备。

服务端按 connectionId 分别登记连接：同一个 deviceId 的新连接与尚未清理的旧连接可以同时在线，不会互相拒绝。旧连接后续由断开事件或保活回收独立移除，不影响新连接。对可靠性要求高时，也可以在 Closed 事件里做带退避的手动重连。

4. 设备端：注册可被调用的方法

设备上线时上报的 methods 只是白名单；真正的方法实现要在 HubConnection 上用 On 注册。服务端调用时使用：

InvokeAsync<string>(methodName, payload)

也就是说，设备的 handler 必须满足：

  • 恰好接收一个 string 参数（即 payload）；
  • 返回 string（同步 Func<string, string> 或异步 Func<string, Task<string>> 都可以）；
  • 方法名与 info.methods 中上报的拼写完全一致（SignalR 客户端注册是区分大小写的）。
// 同步 handler
connection.On<string, string>("Ping", payload => $"pong:{payload}");

// 异步 handler（SDK 有 Func<T, Task<TResult>> 重载）
connection.On<string, string>("Echo", async payload =>
{
    await Task.Delay(10);
    return payload;
});

大小写规则（重要）：

  • /api/invoke 的白名单匹配不区分大小写：请求 "ping" 也能命中上报的 "Ping"。
  • 服务端下发时使用设备上报的精确拼写（"Ping"），而不是请求里的原文。
  • 客户端 On("Ping", ...) 按精确大小写匹配。只要上报与注册的拼写一致，请求端用任意大小写都不会出问题。

handler 必须有返回值：服务端等的是 InvokeAsync<string> 的结果。如果客户端注册的是无返回值 handler（On<string> + Action）、返回非 string、抛异常或 30 秒内不返回，/api/invoke 都会返回 502。

5. 调用端：POST /api/invoke

5.1 请求

POST https://<服务器地址>:6099/api/invoke
Authorization: Basic <Base64("任意用户名:" + 口令)>
Content-Type: application/json
HTTP/2

A. 不指定设备（推荐用于多台设备提供同一能力的场景）：服务端会在所有上报了 method 的在线客户端中均匀随机选一台。

{
  "method": "Ping",
  "payload": "hello"
}

B. 精确指定设备：只调用这一台；它没上报该方法时返回 409。

{
  "deviceId": "pc-001",
  "method": "Ping",
  "payload": "hello"
}
字段类型必填说明
deviceIdstring | null否目标设备 ID。省略、null 或空白时进入全局随机模式；传入时只在 DeviceId 相同的在线连接中选。同一个 deviceId 可能有多条连接，此时在该 ID 下支持 method 的连接中随机选一条。
methodstring是要调用的方法名。只有把它写进 info.methods 的设备才会成为候选（大小写不敏感匹配）。
payloadstring | null否原样作为唯一参数传给设备 handler。省略或为 null 时按空字符串 "" 下发。

随机选择的范围：候选单位是连接而不是 deviceId：先按请求里的 deviceId（若提供）过滤，再按 method 白名单过滤，最后从剩下的连接中均匀随机抽一条。不做轮询、不做会话粘滞。该集合是请求到达时在线表的快照；如果被选中的连接恰好在调用发出前断开，本次请求返回 502，服务端不会自动改选另一条——需要重试时由调用方决定（下一次请求会重新随机）。

怎么知道落到了哪台：响应里的 deviceId / connectionId 是实际承接本次调用的设备与连接。同一 deviceId 可能对应多条连接，connectionId 才是唯一凭证；随机模式下不要拿请求里的值做记录。

5.2 成功响应（HTTP 200）

{
  "deviceId": "pc-001",
  "connectionId": "YbKh5ljC8XH9kHv8US1sng",
  "method": "Ping",
  "result": "pong:hello"
}
  • deviceId 是实际承接本次调用的设备。随机模式下由服务端选出，可能每次不同。
  • connectionId 是服务端为这条连接分配的 SignalR 连接 ID。同一个 deviceId 允许多条连接同时在线，connectionId 是区分它们的唯一凭证。
  • method 是服务端实际下发的精确拼写（即被选中设备上报的那个）。即使请求写的是小写 ping，这里也会回显设备上报的 Ping。
  • result 是设备 handler 返回值的原样透传，类型始终是字符串。

5.3 状态码

状态码含义典型原因
200调用成功设备在线、方法已上报、handler 正常返回 string。
400请求不合法method 缺失 / 空白；请求体不是合法 JSON。deviceId 可省略。
401未通过鉴权缺少 Authorization、不是 Basic、base64 非法、口令不匹配。
404没有可调用的目标全局随机模式：当前没有任何在线连接上报该方法。精确模式：该 deviceId 当前没有任何在线连接（从未上线、已断开、ID 写错）。
409方法未上报仅精确模式：该 deviceId 有在线连接，但没有任何一条在 info.methods 里上报这个方法（大小写不敏感比较后仍无匹配）。全局随机模式不会返回 409——不支持该方法的连接根本不会成为候选。
502端上调用失败设备在调用瞬间断开、客户端没有注册该 handler、handler 抛异常、handler 不返回 string、超过 30 秒未返回。

30 秒上限：服务端等待设备返回值的超时是固定 30 秒。超时后 HTTP 返回 502；设备侧即使之后才返回，也不会再写回这个 HTTP 响应。

5.4 C# 调用示例（HttpClient）

using System.Net;
using System.Net.Http.Headers;
using System.Net.Http.Json;
using System.Text;

const string server = "https://127.0.0.1:6099";
const string clientPassword = "<服务端 ssl/client-password.txt 的内容>";

var handler = new SocketsHttpHandler
{
    SslOptions = { RemoteCertificateValidationCallback = (_, _, _, _) => true }
};

using var http = new HttpClient(handler)
{
    BaseAddress = new Uri(server),
    // 服务端是 HTTP/2 only，普通请求也必须走 h2
    DefaultRequestVersion = HttpVersion.Version20,
    DefaultVersionPolicy = HttpVersionPolicy.RequestVersionExact
};

// Basic：用户名任意，口令取文件内容
var basic = Convert.ToBase64String(
    Encoding.UTF8.GetBytes("admin:" + clientPassword));
http.DefaultRequestHeaders.Authorization =
    new AuthenticationHeaderValue("Basic", basic);

// PostAsJsonAsync 自动完成 JSON 序列化，并设置 Content-Type: application/json

// A. 不指定设备：服务端在所有上报了 Ping 的在线客户端中随机选一台
using var response = await http.PostAsJsonAsync("/api/invoke", new
{
    method = "Ping",
    payload = "hello"
});

// B. 精确指定设备：在匿名对象里加回 deviceId 即可
// using var response = await http.PostAsJsonAsync("/api/invoke", new
// {
//     deviceId = "pc-001",
//     method = "Ping",
//     payload = "hello"
// });

Console.WriteLine($"HTTP {(int)response.StatusCode}");
Console.WriteLine(await response.Content.ReadAsStringAsync());
// 200 {"deviceId":"实际被选中的设备","connectionId":"...","method":"Ping","result":"pong:hello"}

// 成功时也可以直接反序列化为强类型：
// public sealed record InvokeResult(string DeviceId, string ConnectionId, string Method, string Result);
// var result = await response.Content.ReadFromJsonAsync<InvokeResult>();
// Console.WriteLine(result?.Result);

先判断状态码，再反序列化。非 2xx（401/404/409/502）的响应体通常是空的，直接 ReadFromJsonAsync 会抛 JsonException。用 response.IsSuccessStatusCode 或 EnsureSuccessStatusCode() 先分流。

AOT 客户端：PostAsJsonAsync / ReadFromJsonAsync 默认走反射序列化。若调用方是 AOT 发布，改用带 JsonTypeInfo<T> 的重载，并定义 source-gen 的 JsonSerializerContext（与文档开头设备端使用 JsonSerializer.Serialize 的场景分开处理）。

不要用默认的 HTTP/1.1 客户端。HttpClient 默认请求版本是 1.1；必须显式设置 DefaultRequestVersion = HttpVersion.Version20（建议同时用 RequestVersionExact），否则连接会被服务端断开。Git Bash 自带的 curl 通常不支持 HTTP/2，也不适合用来验证这个接口。

PowerShell 7 也可以直接验证（Invoke-WebRequest 支持 -SkipCertificateCheck 与 -HttpVersion 2.0）：

# 在服务端机器上执行：口令从文件读，避免手抄
$pass = (Get-Content .\ssl\client-password.txt -Raw).Trim()
$auth = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("admin:$pass"))

# 精确指定设备；去掉 body 里的 deviceId 即为随机模式
Invoke-WebRequest -SkipCertificateCheck -HttpVersion 2.0 -Method Post `
  -Uri https://127.0.0.1:6099/api/invoke `
  -Headers @{ Authorization = "Basic $auth" } `
  -ContentType 'application/json' `
  -Body '{"deviceId":"pc-001","method":"Ping","payload":"hello"}'

6. 辅助接口：/api/devices、/api/status

两个接口都是 GET，鉴权方式与 /api/invoke 完全相同（HTTP Basic + 同一口令），可用于排障。

6.1 GET /api/devices —— 当前在线设备及方法清单

{
  "total": 1,
  "items": [
    {
      "deviceId": "doc-sample-001",
      "machineName": "DESKTOP-PR0BBBD",
      "userName": "alice",
      "connectionId": "PoHpKFOATQmnNm7Ob2O63A",
      "methods": ["Ping", "Echo"]
    }
  ]
}

返回的是在线连接列表：每条连接一项，total 是连接数而不是去重后的设备数。同一个 deviceId 可能出现多次，用 connectionId 区分。排查 404 / 409 时先看这里：该 deviceId 是否还有在线连接、这些连接的 methods 里到底有没有那个方法。

{

}

7. 完整可运行示例

7.2 Program.cs

using Microsoft.AspNetCore.Http.Connections;
using Microsoft.AspNetCore.SignalR.Client;
using System.Net;
using System.Net.Http.Headers;
using System.Net.Http.Json;
using System.Text;
using System.Text.Json;

var server   = args[0];   // 例如 https://127.0.0.1:6099
var password = args[1];   // 服务端 ssl/client-password.txt 的内容

// ---------- 1. 连接 ChatHub ----------
var info = JsonSerializer.Serialize(new
{
    deviceId = "doc-sample-001",
    machineName = Environment.MachineName,
    userName = "alice",
    methods = new[] { "Ping", "Echo" }
});
var hubUrl = $"{server}/chathub?info={Uri.EscapeDataString(info)}";

SocketsHttpHandler NewHandler() => new()
{
    SslOptions = { RemoteCertificateValidationCallback = (_, _, _, _) => true },
    EnableMultipleHttp2Connections = true
};

var connection = new HubConnectionBuilder()
    .WithUrl(hubUrl, options =>
    {
        options.Transports = HttpTransportType.WebSockets;
        // negotiate 与 HTTP/2 WebSocket 共用的 HTTP 栈（含证书校验）
        options.HttpMessageHandlerFactory = _ => NewHandler();
        // 必须走 HTTP/2，禁止回退 1.1
        options.WebSocketConfiguration = ws =>
        {
            ws.HttpVersion = HttpVersion.Version20;
            ws.HttpVersionPolicy = HttpVersionPolicy.RequestVersionExact;
        };
    })
    .WithAutomaticReconnect()
    .Build();

// 方法名必须与 info.methods 的拼写一致；收一个 string，返回 string
connection.On<string, string>("Ping", payload => $"pong:{payload}");
connection.On<string, string>("Echo", payload => payload);

await connection.StartAsync();
Console.WriteLine($"[hub] connected, connectionId={connection.ConnectionId}");

// ---------- 2. 调用 /api/invoke ----------
using var handler = NewHandler();
using var http = new HttpClient(handler)
{
    BaseAddress = new Uri(server),
    DefaultRequestVersion = HttpVersion.Version20,
    DefaultVersionPolicy = HttpVersionPolicy.RequestVersionExact
};
http.DefaultRequestHeaders.Authorization = new AuthenticationHeaderValue(
    "Basic", Convert.ToBase64String(Encoding.UTF8.GetBytes("admin:" + password)));

static async Task Invoke(HttpClient client, string label,
                         string? deviceId, string method, string? payload)
{
    // deviceId 传 null 时 JSON 里是 "deviceId":null，服务端按随机模式处理
    using var response = await client.PostAsJsonAsync(
        "/api/invoke", new { deviceId, method, payload });
    var text = await response.Content.ReadAsStringAsync();
    Console.WriteLine($"[invoke] {label,-18} HTTP {(int)response.StatusCode} {text}");
}

await Invoke(http, "pinned",           "doc-sample-001", "Ping", "hello");
await Invoke(http, "random-by-method", null,             "ping", "hello");
await Invoke(http, "not-online",       "no-such-device", "Ping", "hello");
await Invoke(http, "not-declared",     "doc-sample-001", "Nope", "hello");

Console.WriteLine($"[devices] {await http.GetStringAsync("/api/devices")}");

await connection.StopAsync();
Console.WriteLine("[hub] stopped");

8. 常见问题排查

现象 / 异常原因与处理
An HttpMessageInvoker instance must be passed to ConnectAsync when using HTTP/2. 在 WebSocketConfiguration 里设了 HttpVersion=2.0，但没有配置 HttpMessageHandlerFactory（SignalR 因此调用了不带 invoker 的 Connect 重载）。补上 handler factory，或改用 WebSocketFactory 自己传 invoker（见 3.5）。
... must not be set on ClientWebSocketOptions when an HttpMessageInvoker instance is also specified. 已经通过 handler 构造了 invoker（配置了 HttpMessageHandlerFactory，或使用了 WebSocketFactory），却在 ClientWebSocketOptions 上设置了证书/凭据/代理/Cookie。把这些配置移到 SocketsHttpHandler 上。
WebSocketException: Unable to connect to the remote server（内层 SocketException / 连接被重置） 没有设置 HttpVersion = Version20，ClientWebSocket 按 HTTP/1.1 连接 H2-only 端点。补上 WebSocketConfiguration 里的 HTTP/2 配置。
The SSL connection could not be established 自签名证书未被信任。联调时在 handler 上跳过校验；生产环境导入证书。
连接被断开 / Recv failure: Connection was aborted 用了 HTTP/1.1。服务端是 HTTP/2 only，确认客户端实际协商到 h2。
info不是合法JSON / info缺少deviceId / 缺少info info 没有 URL 编码、JSON 写错，或 deviceId 为空。用 Uri.EscapeDataString 编码整段 JSON。
同一 deviceId 多连接时，不知道调用落到了哪条 看响应里的 connectionId；/api/devices 也会逐条列出在线连接。服务端允许同一 deviceId 多连接，不会报“重复上线”。
HTTP 401 口令不对或 Header 格式不对。口令来自服务端 ssl/client-password.txt，格式是 Basic Base64("用户名:口令")。
HTTP 404 随机模式：当前没有任何在线设备上报该方法；精确模式：deviceId 写错、设备已断开，或连接还没建立完成。用 /api/devices 确认在线设备与方法清单。
HTTP 409 仅精确模式：该 deviceId 有在线连接，但没有任何一条在 info.methods 里上报该方法。注意上报的是白名单，且大小写不敏感匹配。全局随机模式不会出现此状态码。
HTTP 502 设备端调用失败：没注册 handler、注册名与上报名大小写不一致、handler 不返回 string、handler 抛异常、超过 30 秒。先核对 methods 与 On(...) 的拼写。
客户端 handler 收不到调用 检查是否用 On<string, string>（一个 string 参数），并且方法名与 info.methods 精确一致。

9. 本地实测记录

  • 环境：Windows 11，.NET 11.0.100-rc.2 SDK；服务端为仓库 CoreProxy.Server.Orleans 的 Debug 构建，监听 https://127.0.0.1:6110；客户端为 net10.0 + Microsoft.AspNetCore.SignalR.Client 10.0.12。
  • 连接：HTTPS + HTTP/2 WebSocket（HttpMessageHandlerFactory + WebSocketConfiguration(HttpVersion=2.0)）连接 /chathub 成功，服务端分配 ConnectionId；WebSocketFactory + 显式 HttpMessageInvoker 的等价写法同样实测成功。
  • 配置矩阵：单独设置 HttpVersion=2.0 而不提供 handler，抛 An HttpMessageInvoker instance must be passed...；提供 handler 后又把证书回调设在 ClientWebSocketOptions 上，抛 ... must not be set on ClientWebSocketOptions...；完全不设置 HttpVersion，连接被 H2-only 端点重置。三种失败均在本地复现。
  • 调用：/api/invoke 正常调用返回 200 和 result:"pong:hello"；方法名用小写 ping 同样成功，响应中的 method 回显为设备上报的精确拼写 Ping。
  • 随机选择（3 台虚拟设备实测）：verify-a/verify-b 上报 Ping，verify-c 只上报 Other。不带 deviceId 调用 Ping 共 400 次，全部 200，实际承接设备只有 verify-a（189 次）与 verify-b（211 次）；verify-c 一次都没被选中。调用 Other 20 次则全部落到唯一支持者 verify-c。
  • 随机模式的其他分支：method 写小写 ping 仍命中并回显 Ping；deviceId 为空白字符串按随机模式处理；不带 deviceId 调用无人上报的 Nope → 404；精确指定 verify-c 调用 Ping → 409；精确指定不存在设备 → 404；响应中的 deviceId/connectionId 均为实际承接者。
  • 失败分支：随机模式下无设备支持该方法、或精确模式下设备不在线 → 404；精确模式下方法未上报 → 409；不带凭据 → 401。
  • 同一 deviceId 多连接（实测）：用 deviceId=dup 同时建立 3 条连接（两条上报 Ping，一条只上报 Other）全部成功；/api/devices 返回 total=4（另有 1 台 other-dev），其中 dup 占 3 行。精确指定 dup 调 Ping 300 次，只落到两条支持者（132 / 168 次），从未落到只支持 Other 的连接；调 Other 始终落到唯一支持者；dup 有连接但无人支持 Nope → 409，指定不存在的 deviceId → 404。断开其中一条后在线连接数由 4 变 3，同 ID 的其余连接不受影响；随后同 ID 重连成功，新连接重新进入候选。
  • HTTP/1.1 对照：curl 走 HTTP/1.1 访问同一端点为 Recv failure: Connection was aborted，确认必须使用 HTTP/2。
  • 说明：本地测试关闭了证书校验；生产环境请改为信任服务端证书。
